### FR-55 на PostgreSQL: одновременные открытия

- Уникальный частичный индекс `notifications_once (kind, event_id, user_id) WHERE kind IN ('reply_overdue', 'no_score')`, вставка — `ON CONFLICT (kind, event_id, user_id) WHERE kind IN (...) DO NOTHING`.
- Проверка сроков выполняется транзакцией с рекомендательной блокировкой (`pg_advisory_xact_lock`): одновременные проверки идут по очереди, как прежде с `BEGIN IMMEDIATE` в SQLite.
- На работающей системе в Docker 8 потоков с отдельными подключениями одновременно выполнили проверку сроков: уведомление создала одна проверка (`[0, 0, 0, 0, 0, 0, 0, 1]`), в базе одна запись `no_score` на игру с «Тестовой звездой».
- Автотест `test_unique_index_blocks_duplicate_from_parallel_transaction`: даже без очереди проверок вторая транзакция ждёт первую на уникальном индексе и после её фиксации ничего не создаёт.

### Что сделано

- Режим работы — переменная `TEAMPLAN_MODE` (`demo` по умолчанию, `production`), код одинаков (ТР-6). При запуске контейнера `startup.py`: в `demo` выполняет `seed.py`, как раньше; в `production` только создаёт таблицы и, если организатора нет, пишет в журнал подсказку про `create_organizer.py` (РЗ-7). Неизвестное значение режима останавливает запуск с понятным сообщением. `seed.py` при `TEAMPLAN_MODE=production` отказывается работать и вручную.
- `docker-compose.prod.yml` — дополнение к `docker-compose.yml`: `TEAMPLAN_MODE=production` для приложения; обязательный `POSTGRES_PASSWORD` (пароль демонстрационного режима не используется); сервис Caddy `caddy:2.10.2-alpine` с портами 80 и 443 на всех адресах, `Caddyfile` с доменом из `TEAMPLAN_DOMAIN`, прокси на `teamplan:8501`, заголовок HSTS; сертификаты в томе `caddy-data` (РЗ-1, РЗ-2, ТБ-7). Порты приложения и базы остаются на `127.0.0.1` (РЗ-3).
- Ограничение попыток входа (ТБ-8): `auth.LoginThrottle` — счётчик в памяти приложения под `threading.Lock`, общий для всех сессий. После 5 неверных паролей подряд логин (без учёта регистра) блокируется на 15 минут, в том числе для верного пароля; попытки во время блокировки её не продлевают; успешный вход сбрасывает счётчик; серия неверных попыток забывается, если 15 минут их не было. Пустые поля попыткой не считаются. Счётчик ведётся для любого введённого логина, поэтому сообщение о блокировке одинаково для существующего и несуществующего (FR-2).
- `.env.example`: `TEAMPLAN_MODE` и `TEAMPLAN_DOMAIN` с пояснениями. README: раздел «Размещение на сервере (рабочий режим)». GitHub Actions: задание «Настройки рабочего режима» — `docker compose -f docker-compose.yml -f docker-compose.prod.yml config` с тестовыми значениями и `caddy validate` для `Caddyfile`.

### Замечания

- На сервере сейчас почти пустая база: только организатор, без игроков и событий. Поэтому совпадение на сервере подтверждает весь путь (копия → бакет → скачивание → восстановление → сравнение), но не сравнение данных по существу. Сравнение на данных проверено на демонстрационной базе локально. Перед вводом реальных данных можно повторить проверку на сервере, когда организатор внесёт несколько тестовых записей: `python3 deploy/backup.py create`, затем `python3 deploy/restore_check.py`.
- Системные часы машины в UTC, а часовой пояс приложения — `Asia/Irkutsk` (`.env`). Системный пояс не менялся: время запуска задано в таймере с поясом, имя копии строится по `TZ` из `.env`. `systemctl list-timers` показывает время в UTC (20:00 = 04:00 по Иркутску).
- `restore_check.py` при создании проверочной базы печатает от PostgreSQL `NOTICE: database "teamplan_restore_check" does not exist, skipping`. Это нормально: перед созданием удаляется база, оставшаяся от прерванной проверки, если она есть.
- На сервере рабочая копия репозитория на ветке `backups`. После слияния pull request нужно выполнить `git checkout main && git pull`.
- РК-3 подготовлено, но не включено: вызов `python3 deploy/backup.py create --label predeploy` добавляется в автоматическое развёртывание в работе 11.
