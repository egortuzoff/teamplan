## 1. Общие сведения

**1.1 Полное наименование.** Веб-приложение TeamPlan (далее — система).

**1.2 Заказчик и исполнитель.** Заказчик — преподаватель, выдавший учебное задание. Владелец и основной пользователь — организатор (тренер) команды. Исполнитель — автор проекта.

**1.3 Основания для создания.** Учебное задание: создать приложение или сайт, облегчающий работу или повседневную жизнь, подготовить бизнес-постановку и ТЗ. Бизнес-постановка TP-BP-001 версии 0.17.

**1.4 Плановые сроки.** Жёсткие сроки заданием не установлены.

**1.5 Источники и порядок финансирования.** Расходы на размещение в Яндекс Облаке (виртуальная машина, хранилище резервных копий) покрываются стартовым грантом Облака. Другое финансирование не предусмотрено. Порядок оплаты после окончания гранта — открытый вопрос бизнес-постановки.

**1.6 Порядок оформления и предъявления результатов.** Результаты предъявляются в виде репозитория на GitHub, содержащего исходный код, README, тестовые данные и документы. Заказчик проверяет систему через репозиторий, запуская её локально по README. Рабочая версия для команды размещается на сервере (п. 4.12); вход на неё выполняют только участники команды.

**1.7 Нормативные документы.** ГОСТ 34.602 (структура ТЗ на автоматизированную систему). Актуальная редакция стандарта проверяется перед утверждением.

**1.8 Термины.** Применяются определения из раздела «Термины» бизнес-постановки: событие, явка, состав, результат игры, лента уведомлений, MVP.

## 2. Цели и назначение создания системы

**2.1 Назначение.** Система хранит расписание событий команды, отметки явки на тренировки и мероприятия, составы на игры, результаты игр и уведомления об изменениях, а также показывает статистику игроков.

**2.2 Цели создания:**
- сократить время сбора состава на событие с оценочных 30 минут до не более 5 минут;
- повысить долю игроков, ответивших на тренировки и мероприятия до срока, с оценочных 60 % до не менее 90 %;
- исключить потерю данных об изменениях событий, составов и результатов (0 спорных случаев).

Исходные значения — оценки автора и заменяются замерами. Измерение целевых значений выполняется на тестовом сценарии после приёмки.

**2.3 Границы.** Входит: календарь событий, сводные таблицы по типам событий, явка, сводка, составы с публикацией, список игроков, вход по логину и паролю, счёт, голы и передачи, статистика, внутренняя лента уведомлений, постоянное размещение в Яндекс Облаке с автоматическим развёртыванием и резервным копированием. Не входит: внешние уведомления (почта, Telegram, push), саморегистрация, смена и восстановление пароля игроком, учёт взносов, мобильное приложение, расширенная статистика (минуты, штрафы, рейтинги), автоголы, резервный сервер и отказоустойчивость, управляемая СУБД (переход возможен на следующем этапе, РЗ-8).

## 3. Характеристика объектов автоматизации

**3.1 Автоматизируемые процессы:** планирование событий команды, сбор явки на тренировки и мероприятия, формирование и объявление состава на игру, учёт результатов игр, информирование игроков об изменениях.

**3.2 Текущее состояние.** Анонсы, ответы игроков и составы ведутся в чатах и таблицах. Сообщения теряются, явка подсчитывается вручную, статистика не ведётся.

**3.3 Условия эксплуатации.** Два режима:
- **рабочий** — постоянная работа на виртуальной машине Яндекс Облака; организатор и игроки одновременно работают со своих компьютеров и телефонов через интернет по HTTPS;
- **демонстрационный** — локальный запуск на одном компьютере для проверки по README; пользователи входят под тестовыми логинами по очереди.

Рассчитано на одного организатора и до 30 игроков.

## 4. Требования к системе

### 4.1 Требования к структуре и режимам функционирования

- **ТР-1.** Система реализуется как единое веб-приложение на Python, без разделения на независимые интерфейсную и серверную части.
- **ТР-2.** Система хранит данные в СУБД PostgreSQL версии 17. СУБД работает в отдельном контейнере рядом с приложением (в рабочем режиме — на той же виртуальной машине).
- **ТР-3.** Система работает в одном режиме: штатная работа. Отдельный административный режим не предусмотрен.
- **ТР-4.** Выбор конкретного фреймворка (Streamlit или Flask) выполняется на этапе разработки и фиксируется в README.
- **ТР-6.** Код системы одинаков для рабочего и демонстрационного режима. Режимы отличаются только настройками окружения (п. 4.12).
- **ТР-7.** Адрес подключения к базе задаётся одной переменной окружения `DATABASE_URL`. Перенос базы на другой сервер или в управляемую СУБД не требует изменения кода.

### 4.2 Численность и квалификация пользователей

- **ТР-5.** Система рассчитана на одного организатора и до 30 игроков. В рабочем режиме они работают одновременно со своих устройств, в демонстрационном — на одном компьютере по очереди. Пользователям не требуется специальная подготовка, достаточно инструкции из README.

### 4.3 Функциональные требования

**Вход и аккаунты**

- **FR-1.** Система предоставляет вход по логину и паролю и выход из системы.
- **FR-2.** При неверной паре «логин и пароль» система отказывает во входе и выводит сообщение, не указывающее, что именно неверно.
- **FR-3.** При входе система определяет роль пользователя («организатор» или «игрок») и разрешает только действия, предусмотренные таблицей прав (п. 4.7).
- **FR-4.** Организатор создаёт аккаунт игрока с полями «имя», «логин», «пароль». Логин уникален, при повторе система отклоняет создание с сообщением.
- **FR-5.** Организатор задаёт игроку новый пароль. Игрок не может сменить пароль самостоятельно.
- **FR-6.** Один игрок соответствует одному аккаунту. Организатор может одновременно быть игроком.

**Список игроков**

- **FR-7.** Организатор ведёт список игроков: имя, необязательные игровой номер и позиция.
- **FR-8.** Система запрещает удалять игрока, у которого есть гол, передача или включение в состав. При попытке выводится пояснение.

**События**

- **FR-9.** Организатор создаёт событие с полями: название, тип («тренировка», «игра», «мероприятие»), дата, время, место. Для тренировки и мероприятия доступно необязательное поле «ответить до». Для событий любого типа доступно необязательное поле «время сбора» (FR-41). Для игры доступно необязательное поле «Соперник» (название команды соперника, не более 100 символов), его можно изменить при редактировании. Мероприятие — командное событие вне тренировок и игр, например разбор матча или выезд команды.
- **FR-10.** Система отклоняет создание события с пустым названием или датой в прошлом и выводит причину отказа.
- **FR-11.** Организатор редактирует поля события. При изменении даты, времени, времени сбора или места отметки явки игроков сохраняются.
- **FR-12.** Организатор отменяет событие, которое ещё не началось. Событие остаётся в списке со статусом «Отменено».
- **FR-13.** Организатор удаляет событие, у которого нет результата. Вместе с ним удаляются отметки явки, состав и связанные уведомления.
- **FR-14.** Система запрещает удалять игру, у которой есть счёт или голы, и выводит пояснение.
- **FR-15.** Система показывает список событий, упорядоченный по дате, с типом, временем сбора (если указано) и статусом по FR-48.
- **FR-41.** Время сбора — необязательное время, когда игрокам нужно прийти перед событием. Указывается для событий любого типа, относится к дню события и не может быть позже времени начала. При нарушении система отклоняет сохранение и выводит причину. Время сбора показывается в расписании и в карточке события.
- **FR-42.** Срок «ответить до» при задании или изменении не может быть раньше текущего момента и позже начала события. При нарушении система отклоняет сохранение и выводит причину. Если срок не менялся, редактирование других полей события после наступления срока не блокируется.

**Явка на тренировки и мероприятия**

- **FR-16.** Игрок отмечает свою явку на тренировку или мероприятие: «буду», «не буду» или «под вопросом».
- **FR-17.** Организатор отмечает явку за любого игрока.
- **FR-18.** Новая отметка заменяет предыдущую отметку того же игрока на том же событии.
- **FR-19.** Система запрещает менять отметку явки после начала события.
- **FR-20.** Для события типа «игра» система не предоставляет отметку явки.
- **FR-21.** Система показывает сводку по событию: число ответивших, число не ответивших, список игроков по каждому статусу.
- **FR-22.** После срока «ответить до» система подсвечивает игроков, не ответивших на событие.

**Состав на игру**

- **FR-23.** Организатор выбирает игроков из списка всех игроков и сохраняет состав в состоянии «черновик».
- **FR-24.** Организатор публикует состав, после чего состав переходит в состояние «опубликован».
- **FR-25.** Игрок видит только опубликованный состав. До публикации система показывает надпись «Состав пока не объявлен».
- **FR-26.** Организатор изменяет опубликованный состав. Изменение сохраняется и вызывает уведомление по правилам FR-38.

**Результат игры**

- **FR-27.** Организатор вносит счёт нашей команды и соперника для игры, которая началась и имеет опубликованный состав.
- **FR-28.** Организатор добавляет гол нашей команды с автором и необязательным передающим.
- **FR-29.** Система отклоняет гол, если автор не входит в состав, если передающий не входит в состав, если автор и передающий совпадают. У гола не более одного передающего.
- **FR-30.** Если число голов не совпадает со счётом нашей команды, система выводит предупреждение и сохраняет результат.
- **FR-31.** Организатор редактирует результат.

**Статистика**

- **FR-32.** Система показывает таблицу «игрок, игры, голы, передачи» за всё время.
- **FR-33.** Показатель «игры» равен числу игр с внесённым счётом, в составе которых был игрок.

**Сводные таблицы по типам событий**

- **FR-43.** Расписание разделено на вкладки «Все», «Игры», «Тренировки», «Мероприятия». Вкладка «Все» показывает общий список по FR-15, остальные — только события своего типа. Порядок строк — по дате и времени, отменённые события остаются в таблицах с пометкой «Отменено».
- **FR-44.** Таблица игр содержит: дату, время, время сбора, название, соперника (если указан), место, счёт в виде «наша команда : соперник», итог («Победа», «Ничья», «Поражение»), статус по FR-48. Итог вычисляется по счёту. Если счёт не внесён, в колонках «Счёт» и «Итог» стоит прочерк.
- **FR-45.** Таблицы тренировок и мероприятий содержат: дату, время, время сбора, название, место, число ответов «буду», «под вопросом», «не буду», число не ответивших, статус по FR-48.
- **FR-46.** Выбор строки в любой из таблиц расписания открывает карточку этого события.
- **FR-47.** В карточке игры с внесённым результатом всем пользователям показываются счёт и список голов нашей команды. Счёт показывается в виде «Счёт: 3 : 1 (ХК «Иркутский Политех» : <соперник>)»; если соперник не указан, вместо названия пишется «Соперник». В списке голов имя автора выделено жирным, передающий (если указан) — в скобках без слова «передача», например: «**Игрок Первый** (Игрок Второй)». Название нашей команды задаётся в одном месте настроек приложения.
- **FR-48.** Статус события для показа вычисляется автоматически: «Отменено» — событие отменено; «Запланировано» — событие ещё не началось; «Прошло» — тренировка или мероприятие уже начались; «Сыграна» — игра началась и счёт внесён; «Счёт не внесён» — игра началась, а счёт не внесён. Статус показывается в расписании, сводных таблицах, карточках ближайших событий и карточке события. В базе по-прежнему хранится только признак отмены.

**Главный экран**

- **FR-49.** После входа игрок видит главный экран: блок «Следующее событие» (тип, дата, время, соперник для игры, место, время сбора, через сколько дней; для игры — пометка «Вы в составе», если игрок входит в опубликованный состав) с переходом к карточке события и ко всему расписанию; блок «Последний матч» (счёт в виде FR-47, итог, дата, авторы голов), если есть сыгранная игра; блок «На этой неделе» — карточки событий ближайших 7 дней, для тренировок и мероприятий с кнопками явки «Буду», «Под вопросом», «Не буду» прямо в карточке по правилам FR-16 – FR-19; блок «Моя статистика» (игры, голы, передачи по FR-32, FR-33).
- **FR-50.** После входа организатор видит главный экран: блок «Требует действия» — ближайшая игра с неопубликованным составом, с кнопками «Опубликовать состав» и «Изменить состав»; кнопки «+ Тренировка», «+ Игра», «+ Мероприятие», открывающие форму нового события с выбранным типом; блок «Счёт не внесён» — прошедшие игры без счёта со ссылкой на внесение результата; блок «Явка на неделе» — для тренировок и мероприятий ближайших 7 дней число ответов «буду», «под вопросом», «не буду», «не ответили» и список не ответивших. Пустые блоки не показываются или показывают короткое пояснение («Ближайших событий нет»).
- **FR-51.** Главный экран находится в разделе «Расписание» над вкладками FR-43 и заменяет прежние карточки ближайших событий. Все действия на главном экране выполняются по тем же правилам и с той же проверкой прав, что и в карточке события.

**Лента уведомлений**

- **FR-34.** Система создаёт уведомления в случаях и для получателей, указанных в таблице п. 4.5, в том числе уведомления организатору по FR-52 – FR-54.
- **FR-35.** Система не создаёт уведомление организатору о его собственных действиях.
- **FR-36.** Игрок видит только свои уведомления.
- **FR-37.** Лента показывает последние 50 уведомлений, непрочитанные визуально отличаются от прочитанных.
- **FR-38.** При изменении опубликованного состава уведомление получают игроки прежнего и нового состава.
- **FR-39.** Система показывает число непрочитанных уведомлений после входа.
- **FR-40.** Уведомление становится прочитанным при открытии. Пользователь может отметить все уведомления прочитанными одним действием.
- **FR-52.** Когда игрок сам отмечает явку на тренировку или мероприятие, организатор получает уведомление: при первом ответе «Под вопросом» или «Не буду» и при любом изменении уже данного ответа. Первый ответ «Буду» уведомления не создаёт. Уведомление содержит игрока, событие, прежний и новый ответ. Отметка, которую ставит сам организатор, уведомления не создаёт (FR-35).
- **FR-53.** Когда наступил срок «ответить до», а у события (не отменённого) есть не ответившие игроки, организатор получает одно уведомление со списком не ответивших. Повторно для того же события оно не создаётся.
- **FR-54.** Когда игра (не отменённая) началась, а счёт не внесён, организатор получает одно уведомление с предложением внести результат. Повторно для той же игры оно не создаётся.
- **FR-55.** Уведомления FR-53 и FR-54 создаются без отдельного фонового процесса: система проверяет наступление сроков при открытии или обновлении любой страницы любым пользователем. Проверка не создаёт дубликатов при одновременных и повторных открытиях.

### 4.4 Показатели назначения, надёжности и эргономики

- **НТ-1.** Отклик системы на действие пользователя не превышает 2 секунд при 30 игроках и обычном настольном компьютере.
- **НТ-2.** Данные сохраняются после остановки и повторного запуска системы.
- **НТ-3.** При некорректном вводе система выводит сообщение на русском языке с причиной и не завершается аварийно. Технические сообщения об ошибке пользователю не показываются.
- **НТ-4.** Язык интерфейса — русский.
- **НТ-5.** Система работает в настольных версиях браузеров Chrome, Firefox и Edge текущих версий.
- **НТ-6.** Система запускается по инструкции из README на чистой системе без правки кода.
- **НТ-7.** Оформление «Табло»: тёмный фон, светлый текст, меню разделов сверху; шрифты Oswald (заголовки), Golos Text (текст), JetBrains Mono (цифры счёта и статистики) из Google Fonts. Контраст текста к фону не ниже 4.5:1, крупного текста (от 24 px) — не ниже 3:1. Цвет не единственный признак статуса: у статусов есть подписи.
- **НТ-8.** В рабочем режиме система работает также в мобильных браузерах текущих версий: Яндекс Браузер (Android и iOS), Chrome (Android и iOS), Safari (iOS), Samsung Internet (Android), Firefox (Android); на экране шириной от 360 px основные действия (вход, явка, просмотр расписания, состава и статистики) выполняются без горизонтальной прокрутки страницы.

### 4.9 Требования к серверной части и интеграциям

- **ТС-1.** Отдельный публичный API не предусмотрен. Раздел сохраняется с записью об отсутствии требований.
- **ТС-2.** Внешние интеграции в работе системы не предусмотрены. Для размещения используются сервисы Яндекс Облака и GitHub Actions (п. 4.12, 4.13); пользовательские данные в GitHub не передаются.
- **ТС-3.** При ошибке записи в базу система не теряет ранее сохранённые данные, сообщает пользователю о неудаче и позволяет повторить действие.

### 4.10 Требования к безопасности

- **ТБ-2.** Пароли хранятся только в виде хеша с солью. Пароль в открытом виде не хранится, не выводится на экран и не записывается в журналы.
- **ТБ-3.** Для хеширования используется проверенная библиотека, собственная реализация шифрования не допускается.
- **ТБ-4.** Для событий, составов и результатов система хранит время создания и последнего изменения.
- **ТБ-5.** В репозиторий не попадают реальные данные и реальные пароли. Тестовые данные вымышленные.
- **ТБ-6.** В демонстрационном режиме приложение доступно только с компьютера, на котором оно запущено (порт открыт только для localhost). Доступ в рабочем режиме — по РЗ-3.
- **ТБ-7.** В рабочем режиме обмен с браузером выполняется только по HTTPS с действующим сертификатом. Запрос по HTTP перенаправляется на HTTPS.
- **ТБ-8.** После 5 неверных попыток входа подряд для одного логина вход под этим логином блокируется на 15 минут; сообщение об этом не раскрывает, существует ли логин. Счётчик попыток может храниться в памяти приложения и сбрасываться при перезапуске.
- **ТБ-9.** Персональные данные игроков ограничены именем, логином, игровым номером и позицией. Данные рабочего режима хранятся только на сервере в Яндекс Облаке (регион Россия) и в резервных копиях; в репозиторий, журналы GitHub Actions и материалы проекта они не попадают. Согласие игроков на хранение данных организатор получает до их ввода (организационная мера, вне системы).

### 4.11 Требования к программному и информационному обеспечению

- **ТП-1.** Язык реализации — Python. Версия Python и список зависимостей фиксируются в репозитории. Для запуска без Docker поддерживаются Python 3.12 и 3.13. Рекомендуемый способ запуска — Docker (ТП-3), в нём версия Python задана образом.
- **ТП-2.** Для установки зависимостей используется файл со списком зависимостей в репозитории.
- **ТП-3.** Система поставляется с упаковкой для запуска в Docker: в репозитории есть Dockerfile и инструкция сборки и запуска через Docker Desktop на Windows. Сборка и запуск выполняются не более чем двумя командами.
- **ТП-4.** При запуске в Docker данные PostgreSQL хранятся в томе Docker вне контейнера и сохраняются при пересоздании контейнеров.
- **ТП-5.** Автоматические тесты в GitHub Actions выполняются на PostgreSQL 17. Проверка Docker в GitHub Actions запускает приложение вместе с СУБД.

### 4.12 Требования к размещению и развёртыванию

- **РЗ-1.** В рабочем режиме система размещается на одной виртуальной машине Яндекс Облака (Ubuntu LTS, Docker и Docker Compose). На машине работают контейнеры приложения, PostgreSQL и обратного прокси, который обслуживает HTTPS.
- **РЗ-2.** Система доступна по доменному имени. Используется бесплатное доменное имя (сервис динамического DNS) и бесплатный сертификат Let's Encrypt с автоматическим продлением. Конкретный сервис и адрес фиксируются в README.
- **РЗ-3.** Из интернета открыты только порты 80 и 443 (веб) и 22 (SSH). Порт приложения и порт PostgreSQL снаружи недоступны. Вход на машину по SSH — только по ключу, вход по паролю отключён.
- **РЗ-4.** После слияния изменений в ветку main и успешного прохождения всех проверок GitHub Actions автоматически обновляет систему на машине: получает новую версию кода, пересобирает и перезапускает контейнеры. Если проверки не пройдены, обновление не выполняется. Данные при обновлении сохраняются. Обновление можно запустить вручную из GitHub Actions.
- **РЗ-5.** После обновления GitHub Actions проверяет, что приложение отвечает по HTTPS. Если приложение не ответило, запуск отмечается как неудачный.
- **РЗ-6.** Секреты (SSH-ключ и адрес машины для развёртывания) хранятся в GitHub Secrets. Пароль базы и другие настройки рабочего режима хранятся в файле `.env` на машине. В репозитории есть только образец `.env.example` без настоящих значений.
- **РЗ-7.** В рабочем режиме тестовые данные не загружаются. Аккаунт организатора создаётся командой `create_organizer.py`, игроков заводит организатор.
- **РЗ-8.** Переход на управляемую СУБД (Managed Service for PostgreSQL) — отдельный будущий этап. Он выполняется сменой `DATABASE_URL` (ТР-7) и переносом данных из резервной копии без изменения кода. Решение принимается по итогам пробной эксплуатации и бюджету.

### 4.13 Требования к резервному копированию

- **РК-1.** В рабочем режиме полная копия базы создаётся автоматически не реже одного раза в сутки.
- **РК-2.** Копии хранятся вне виртуальной машины, в Yandex Object Storage, в закрытом бакете. Хранятся копии не менее чем за 14 последних дней, более старые удаляются автоматически.
- **РК-3.** Перед каждым автоматическим обновлением системы (РЗ-4) создаётся внеочередная копия.
- **РК-4.** Порядок восстановления из копии описан в README. Восстановление проверено до ввода реальных данных: копия разворачивается в пустую базу, данные совпадают с исходными.

## 6. Порядок разработки

- Разработка ведётся этапами. Этап 2 начинается после прохождения проверок этапа 1. Этап 3 (размещение) выполняется в порядке работ 9 – 13 раздела 5; реальные данные вводятся только после прохождения AC-24 (восстановление из копии).
- Разработка выполняется с помощью нейросети из списка, разрешённого заказчиком.
- Каждый промпт содержит версию ТЗ, задачу, перечень файлов, стек и проверки. Требования из ТЗ в промпте не пересказываются и не расходятся с ТЗ.

- После каждого этапа результат проверяется по разделу 7 до перехода к следующему.
- Исходный код хранится в репозитории, изменения фиксируются отдельными записями.

## 7. Порядок контроля и приёмки

**7.1 Виды проверок.** Проверка по тестовым сценариям на тестовых данных, сверка статистики с ручным подсчётом, запуск по README на чистой системе, проверка рабочей версии на сервере (AC-22 – AC-26) без реальных данных или до их ввода.

**7.2 Принимающие.** Заказчик (через репозиторий) и автор.

**7.3 Тестовые данные.** Один организатор, три вымышленных игрока, одна тренировка со временем сбора, одно мероприятие и одна игра с составом из двух игроков и счётом 2:1. Используются только в демонстрационном режиме и в автоматических тестах; на сервер не загружаются (РЗ-7).

## 8. Подготовка объекта автоматизации к вводу в действие

- Демонстрационный режим: установка Python и зависимостей по README либо установка Docker Desktop на Windows для запуска в контейнере.
- Рабочий режим: создание виртуальной машины и бакета Object Storage в Яндекс Облаке, получение доменного имени, заполнение `.env` на машине и GitHub Secrets по README, первое развёртывание, проверка восстановления из копии (AC-24).
- Создание учётной записи организатора на сервере (`create_organizer.py`) и ввод списка игроков вручную после получения их согласия (ТБ-9). Перенос данных из демонстрационного режима не выполняется.
- Загрузка тестовых данных — только в демонстрационном режиме.
- Резервные копии создаются автоматически (п. 4.13). Откат: отмена неудачного изменения в репозитории (новый коммит, который снова проходит развёртывание по РЗ-4) и при необходимости восстановление базы из копии, сделанной перед обновлением (РК-3).
- Обучение пользователей — по инструкции из README.
